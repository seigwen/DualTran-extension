### Added
- **Client-route roundtrip scenarios for the new canary sites** (plan 36, issue #123, user request). The plan-34 sites carried only a single `goto → translate` health assertion; back/forward roundtrip pressure lived exclusively on github.com (Turbo) and the hermetic mock pages. Five new scenarios (`roundtrip-nextjs` / `roundtrip-nuxt` / `roundtrip-svelte` / `roundtrip-angular` / `roundtrip-vercel`) now translate the site home, client-route to a stable subpath (`/docs` / `/modules` / `/docs` / `/tutorials` / `/about` — each measured in a real browser; `/docs/4.x` on nuxt and `/docs` on angular client-redirect, so the stable final URLs are used directly), translate again, then hammer 6 back/forward rounds — every hop asserts a healthy floating host and the VISIBLE translation staying real. Two structural guards close the new false-green/silent-degradation holes: (1) **same-document premise guard** — `tests/shared/document-identity.mjs` compares `performance.timeOrigin` plus a per-document token around navigations; a site redesigned to full-page navigations (or route drift) reports **SKIP-DATA** (audit the scenario) instead of silently becoming a shallow reload test, and `CANARY_SIMULATE_FULLLOAD` (calibration-only) exercises that path deterministically; (2) **visible-scoped quality reads** (`quality.visibleOnly`) — stale hidden DOM from previous routes keeps its translated text and inflated the counters (measured ~+5–10 elements per hop on nextjs), which could mask a reverted visible translation. Sites excluded with evidence (probe archive `probe-archive-2026-09-30/`): astro.build / gitlab.com (full-page navigations), workers.dev (no in-page links). RED-first cells: `tests/shared/documentIdentity.test.js` (7 cells) + `translationQuality.test.js` visibleOnly cells ⑪⑫⑬ — 7 red / 14 green under the naive stubs, archived before implementation.
- **Multi-site canary matrix + translation-reality gate + typed-skip discipline** (plan 34, issue #114). The real-site canary grew from 3 github.com scenarios to **13 scenarios over 10 sites**: github.com ×3 (bug8 / bug7 / selfheal), the issue-#78 carriers workers.dev ×2 and vercel.com ×2 (translation-reality + a seeded off-screen saved-position scenario asserting the floating layer clamps back into view — the user-visible #78 lock), and six front-end-stack representatives nextjs / nuxt / svelte / angular / astro / gitlab ×1 each (selection by stack representativeness, calibrated against CI matrix run 36602259652). x.com joins as a **local-only layer** (`LOCAL_SCENARIOS` + `--include-local`; the deep issue-#98 "Show more" check is the on-demand `scripts/xcom-showmore-check.mjs` with a SKIP-DATA outcome for loads without a truncated post) because Cloudflare blocks the Actions runner IP range — measured attribution: same-stack local Playwright passes (200), CI curl (403) and CI real-Chrome (307) both fail, so it is IP reputation, not a Playwright fingerprint (archived as `xcom-cloudflare-cause.md`). The old "any `<translated>` node exists" assertion had two measured false-green holes — a Google-429 window PASSED bug7 with all 150 nodes empty, and an unseeded profile resolved to `en` so "translated" text was the English source (149 non-empty / 0 CJK). Both are closed by the shared gate `tests/shared/translation-quality.mjs`: the run seeds `targetLanguage=zh-CN`, and every translate / assert-translated step must reach `nonEmpty ≥ max(10, 20%×count)` ∧ `cjk/nonEmpty ≥ 30%` (scenario-level `quality` overrides). Throttle windows are now honest, not green or red: exit codes `0`=PASSED / `1`=FAILED / `2`=SKIPPED-ENV (gtx preflight before the run, failure re-probe during it; a SKIP never opens or closes issues, is never retried, and lets the release gate through with a workflow `::warning::`). RED-first unit suite `tests/shared/translationQuality.test.js` (11 cells; two false-green reproduction cells red under the old semantics, archived); live drills: clean self-test 11/13 PASS exit 0, simulated-throttle preflight and attribution paths both exit 2 (`CANARY_SIMULATE_THROTTLE`, calibration-only, never set by workflows), workflow attempt/evaluate three-state logic verified by a local bash drill.
- **AI reasoning depth selector in the options page** (plan 32): the AI section now carries a reasoning-depth dropdown between the model select and the custom-provider area. Its options are **generated from what the selected provider + model declare in models.dev** (`reasoning_options`) and clipped to what each AI-SDK dialect actually accepts — declarations are a cross-ecosystem union (mistral declares `max`, xai declares `xhigh`), and sending an unaccepted value makes the SDK throw `invalid provider options`, which aborts the whole translation; a dialect that cannot carry the parameter (the thin `@ai-sdk/{togetherai,perplexity,deepinfra,cerebras}` wrappers, which read no `reasoningEffort`) simply falls back to sending nothing. `toggle`-only models expose `Default` + `High`; `budget_tokens`-only models keep just `Default` this round. The single source of truth for the mapping is `src/lib/ai/reasoningDepth.js` (`resolveDialect` / `buildReasoningDepthOptions` / `buildProviderOptions`), consumed by both the options page and `aiProxy.js`, so the SDK client choice and the parameter dialect can never drift apart (the issue #88 lesson). The selection rides the existing transport chain (`providerConfigs[provider].reasoningDepth` → `fetchSSE` → `sseClient` port field → `streamText({ providerOptions })`) and joins the persistent AI translation cache key as a fifth segment — changing the depth now yields a different translation instead of silently reusing the old depth's cached text. Test anchors: `tests/ai/reasoningDepth.test.js` (28 cells: dialect resolution, value clipping, toggle expansion, reject→drop), `tests/background/aiProxyReasoningDepth.test.js` (drives the port `start` message and captures the `providerOptions` handed to `streamText`), `tests/background/aiTranslationCacheReasoningDepth.test.js` (depth participates in the key; pre-upgrade 4-segment entries do not match), plus `tests/options/options.test.js` and E2E `settings-translation.mjs` S12 (pick provider → model → depth → reload → persisted and re-selected) and E2E `reasoning-depth.mjs` (the depth genuinely reaches the wire: the mock server's request log must contain `reasoning_effort: "high"`, and the `Default` control group must carry no reasoning field at all).
- **User feedback channel: one-click prefilled GitHub issue from the error icon + static entries** (plan 35, issue #116). The extension previously had **zero in-product feedback entry points**. Now a block-level error icon (⚠, the only moment the user is demonstrably holding a bug) opens the GitHub issue form **in one click** with the context already filled: version, browser, OS, translation service (Google / AI + provider mapped to the form's exact option values), language pair, hostname, and the actual error text (≤500 chars). The form arrives as a **visible, editable draft** — the user reviews and deletes anything before submitting; nothing is ever sent silently, and no telemetry is introduced. Red line enforced structurally: `buildIssueUrl` / `formatDiagnosticsBlock` destructure a whitelist, so API keys, API base configs, page content and translation text cannot leak even if a caller passes extras (locked by tests). Static entries mirror the same flow where the page context is unknown: the options page gains a **"Report a problem" section** (nav + `#feedback`): an "Open GitHub issue form" button prefills version/browser/OS only (no service claim — a wrong guess misleads triage), "Copy diagnostic info" puts the environment block on the clipboard, and a no-GitHub-account fallback line offers the support email (version-stamped `[DualTran v…]` subject, diagnostics block as a deletable draft) plus the Chrome Web Store support section. Entry points: options feedback section, popup ("Report a problem" row under "More options"), the mobile dropup menu, and the clickable ⚠ error icon (one step to the prefilled form). URL budget: the final URL stays ≤2000 chars by shrinking only the error text (CJK worst-case convergence; every other context field is never dropped — asserted). i18n: 6 new keys added to `en` + hand-translated `zh_CN`/`zh_TW`, the other 36 locales fall back to English; the long-orphaned `lblReport` ("Report a problem", present in all 38 locales with zero call sites) is now actually wired. Test anchors: `tests/lib/feedbackLink.test.js` (20 cells: URL golden strings, whitelist no-leak, service mapping, CJK budget convergence, diagnostics line gating, mailto), `tests/contentScript/feedbackReporter.test.js` (delegated click contract), SW effect builder + dispatch-loop/flow integration cells, options/popup/popupMobile entry cells (RED-first), and E2E `feedback-entry.mjs` F1–F5 (structure, per-parameter URL assertions, clipboard red-line sentinel, popup entry, and the full chain: connection-refused AI error → ⚠ → prefilled URL asserted, login-wall `return_to` decoded when the runner is not signed in).

### Fixed
- **Production build wrote to the user's DevTools console** (plan 39, #131): the store build (measured on the published 2.1.30 CRX) printed 13 console messages in a minimal repro — 10 from the service worker, 2 from the content script on every page translation, 1 from the options page — and 404'd `darkmode.js` on every options-page load. Root cause of the console noise: `webpack.production.js` sets terser `drop_console: true`, but terser only removes console calls it can prove dead; six references reached console through forms it cannot see through (computed `console[level] || console.log`, value-position `log: console.log` x2 / `logError: console.error`, default parameter `onWarn = console.warn`, a `typeof console` guarded read) and shipped verbatim. Fix: rewrite each into literal-call shapes terser can prove dead (fixed-arity arrows; `emitDualTranDebugLog` becomes two literal branches; options.js routes misses through a module-level `debugLog` sink declared above every `$()` call site). No terser config change — the array form was measured to unearth 70 previously-suppressed latent messages and is rejected. The dangling `options/options.html` reference is removed (the file is not in the CopyWebpackPlugin list and is an ES module loaded as a classic script, so it never worked). New artifact-level guard `tests/manifest/buildArtifactGuards.test.js`: AST scan of `dist/chrome/**/*.js` for any console member access (AST, not regex — the bundles legitimately contain eight console.* provider URLs) plus on-disk resolution of every local `<script src>` / `<link href>` in `dist/chrome/**/*.html` (first gate in the repo to catch dangling assets; the E2E benign-404 allowlist and fatal-source set did not cover this class). RED->GREEN: guard 4 failed / 17 passed on master's dist -> 21/21; product AST refs 7 -> 0; live Playwright probe 13 -> 0 messages with translation intact; full vitest 2350 passed.
- **GitHub-facing templates no longer contain hardcoded Chinese** (#121): the bug-report form's four advanced-QA fields (`state-anomaly` / `spa-site` / `state-recover` / `state-steps`) and the PR template's State/Lifecycle section were written in Chinese, but GitHub renders these static repository files with no i18n mechanism — a non-Chinese reporter hit a half-Chinese form exactly at the fields that exist to sharpen triage. Both are rewritten in English (field `id`s and `required` flags unchanged; the `feedbackLink.js` prefill URLs are untouched). A new static guard `tests/static/githubTemplates.test.js` (RED-first: 29 lines flagged pre-fix; negative-fixture detector self-tests) covers the user-facing `.github/` surface by dynamic enumeration (a newly added template is in scope automatically), freezes the `bug_report.yml` field-id set (the prefill + E2E contract), and asserts every dropdown value the extension can prefill (`service` / `browser`) exists byte-for-byte among the form options — a mismatched value makes GitHub silently drop the prefill. Workflows (internal comments only, never rendered) are deliberately out of scope.
- **x.com "Show more" revealed text was never translated** (#98): the dynamic-content MutationObserver classified every `characterData` mutation as "the extension writing its own translation result" and skipped it unconditionally (the #16 feedback-loop guard). But React/site code rewrites existing text nodes in place too (`nodeValue` assignment → characterData; x.com's "Show more" expands a truncated post this way), so the expanded text never re-entered the translation pipeline — the translation stayed frozen at the truncated preview length. Fix: classify characterData mutations **by value** instead of blanket-skipping — a text node whose current data equals the value the extension last wrote (`extensionTextWrites.markTextWrite`) is a self-write and is skipped; anything else is a host update, is queued, and re-queues the piece that references the node (`isTranslated=false`) so the next tick re-reads the expanded text and re-translates it. Two supporting fixes: the same blanket skip also swallowed site updates inside `.dualtran-result-container` in replaceOriginal mode (that class sits on the SOURCE container) — the filter now excludes only marked DualTran-generated nodes (`isDualTranGeneratedNode`, extended with the block indicator), and a freshness guard drops translation responses whose source text changed while the request was in flight (bounded by `STALE_DROP_LIMIT`, so a node whose text outruns the request round-trip cannot spin the loop). newLine re-translation now REUSES the existing google/ai spans instead of appending a second pair. Test anchors: `tests/contentScript/mutationObserver.characterData.test.js` (8 cells: host-update detection, self-write skip, value-comparison semantics, `<translated>` guard, no-op rewrite, re-translation request payload, re-scan of unreferenced nodes, notranslate opt-out — RED-verified 4/4 positive cells under the old blanket skip) + E2E `dynamic-content-showmore.mjs` Scenario B (in-place characterData update; pre-fix RED: "translation stayed at max 75 chars while the source container grew to 517"). Real-site verified on x.com (clicked a truncated long post with a client-hints-spoofed browser; expanded text translated on the fixed build). Feedback-loop guard re-verified: `observer-feedback-loop.mjs` all 4 soak combinations stable.
- **Module-load visibility-timer callback no longer leaks failures** (#96): the 120ms module-load timer's callback chain (tab-visibility check → `detectTabLanguage` → auto-translate decision) is now contained — a failure on any step is warned (`console.warn`) and skipped, never thrown. This is a best-effort check (the user can always translate manually), and an escaped error could previously be reported as an unhandled error that failed the zero-tolerance test job even when every test passed (master `34f0e01`). Auto-translate behavior on healthy environments is unchanged; the #47 teardown guard is preserved. Test anchor: `tests/contentScript/pageTranslatorHelpers.test.js`「T10」.
- **Block-level AI loading indicator flashed for ~45ms and was effectively invisible** (#90): clicking the page-level "AI" button showed no purple spinner on the paragraphs, while clicking "Google" showed the green one. The spinner WAS inserted, then removed again 42ms later — before any AI text arrived (measured: add t=6ms, remove t=48ms, first arrival t=2068ms). Root cause: `aiTranslateDynamically` cleared the indicators right after `await aiTranslateText(...)`, but `aiTranslateText` returns at DISPATCH time (the stream arrives via callbacks) — unlike the Google path, whose `backgroundTranslateHTML(...)` is a real promise that resolves on arrival. Fix: `aiTranslateText` gains an optional per-block settle callback (`onBlockSettled`), and the indicator cleanup is bound to each block's terminal state (translated / error / discarded), with a 180s guard for silently dead streams. The error tooltip now also carries the REAL error message (`proxy._st().errorMessage`; the previous `proxy._lastErrorMessage` never existed and always fell back to a generic string). Anchors: the AI spinner now lands inline at the end of the text being read (newLine: before the `<translated>` container, i.e. tailing the source text like Google's; replaceOriginal: appended inside the block), instead of on a standalone line below the block. RED evidence: `tests/contentScript/aiBlockIndicator.integration.test.js` (5 cells, all red pre-fix) + E2E `ai-block-indicator.mjs` (both display modes; pre-fix build failed with "19 AI spinner(s) removed BEFORE their block's text arrived").
- **Gemini (and any aliased provider ID) silently fell back to the OpenAI-compatible client** (#88): `createModelClient` looked up models.dev provider data with DualTran's internal ID (`google-gemini`), but models.dev keys the entry `google` — the dedicated `@ai-sdk/google` client was never selected, so requests went to a `/chat/completions` URL against the native `generateContent` API. Surfaced by the hardened multi-provider E2E (was silently skipped before). Fix: single source of truth `INTERNAL_TO_MODELSDEV` + `resolveModelsDevId()` in `providerRegistry.js`, consumed by `aiProxy.js`, `sseClient.js` (fallback fetch) and `providerModelPreview.js`. RED tests: `tests/ai/createModelClient.test.js` C5.1–C5.3.
- Mock server Gemini fidelity (#88): `:streamGenerateContent` now answers with SSE frames (was plain JSON — the SDK's SSE parser produced zero chunks), and tag extraction is format-aware (`contents[].parts[].text`, not only `messages[].content`).

### Changed

The bubble that pops up the original text when hovering a translated paragraph (the "Show original text when hovering" setting) no longer fires in newLine mode — with the original text already visible in that mode, hovering to show it again was redundant. The gate is a single predicate in `showOriginal.js` (`showOriginalTextWhenHovering === "yes"` ∧ `whereToDisplayTranslatedText === "replaceOriginal"`) that every registration guard inherits through `showOriginal.isEnabled`, so `pageTranslator.js` needed zero changes. Runtime coupling follows the existing switch semantics: a change of either setting recomputes the predicate, rebuilds or tears down the bubble host, and notifies the page — an already-translated page re-renders once through the observer chain, so flipping the display mode makes the bubble appear/disappear immediately. The options page carries an explanatory note under the setting (`lblShowOriginalTextWhenHoveringNote`, hand-translated en/zh_CN/zh_TW, other 36 locales fall back to English). The bubble's skin is now the shared panel skin: `translateSelected.css` + the `panelShared.js` dark/light constants (same single source the hover translation box and the selection panel consume — no local stylesheet), with ids aligned to the panel vocabulary (`#eDivResult` / `#eOrigText`) and `showOriginal.css` deleted. No title bar, copy button, or dropdown — the bubble stays a pure reading snapshot; trigger and lifecycle (1.5s hover, cursor-follow, retarget on move, destroy on outside click, blur/visibilitychange) are unchanged. Test anchors: `tests/contentScript/showOriginal.test.js` (18 cells: gate 4-combination truth table, both coupling directions, shared template over `translateSelected.css`, dark/light constant blocks), E2E `options-behavior.mjs` O-B (three phases: newLine negative — hovering a `<translated>` block must not raise the host count; replaceOriginal positive — the mode flip re-renders the translated page through `font[data-dualtran-encapsulated]` and hovering the encapsulated font raises the bubble; options-page note structure) and `popup-behavior.mjs` P-B (explicitly pins replaceOriginal and hovers the encapsulated font, restoring both keys afterwards).

- **Single-word AI lookups always issue a live request** (plan 33, #111): clicking the panel's AI button with a single word selected no longer consults the shared in-page cache — a cached plain translation of that word (written by the page / hover text paths) used to be served verbatim as the "dictionary" answer, while what the user wants when looking up a single word is the detailed entry (original form, senses, examples, etymology). The word path is now fully decoupled from the cache in both directions: it never reads it (every click, including a repeat click on the same word, is one live AI call — accepted cost) and never writes it (a dictionary-style result can no longer be served as a paragraph translation by the page / hover paths). The word/sentence split reuses the existing `wordsCount() === 1` routing predicate; the text path's cache reuse is unchanged (pinned by a negative-control E2E cell). Test anchors: `tests/contentScript/translateSelected.test.js`「translateSelected aiTranslateWord」(two cells, both RED pre-fix: a completed run writes nothing; a matching cache entry is ignored — live request issued, pool untouched); E2E `selected-panel.mjs` phases E/F (two consecutive word clicks = two live requests, pre-fix RED; a sentence re-click still hits the cache with zero requests).

### Fixed
- Options page → Hotkeys: the first row of the "Keyboard shortcuts" list no longer renders an empty label. The browser's reserved action command (`_execute_action`, reported by `chrome.commands.getAll()` with an empty description) now gets a localized fallback label (`lblActivateTheExtension`, "Activate the extension" / "激活扩展程序") — previously only the legacy MV2 name `_execute_browser_action` was covered (#85).
- Extension-wide: platform detection no longer treats the existence of the `browser` namespace as "this is Firefox". Since Chrome 148, Chrome exposes extension APIs under `browser` as an alias of `chrome` (without `commands.update`), which made the options page take the Firefox branch on Chromium — showing the in-page shortcut list (and hiding the working "Open native shortcut key manager" button), and made `twpConfig.import` / `twpConfig.restoreToDefault` throw `TypeError: browser.commands.update is not a function` (config import aborted before reload and misreported "file is corrupted"; "Restore default settings" silently did nothing). Detection now probes the `commands.update` capability, so Chrome ≤147 / Chrome 148+ / Firefox all behave correctly (#85).
- Hover AI button: the green ✓ success glyph next to the "AI" label is gone (#83). The success state is still carried by the `dualtran-ai-success` class and the button's active highlight — the label now stays a plain "AI" with no trailing decoration, on both the per-block hover group and the selected-text panel. The error ✕ is unchanged.
- Floating button group: the viewport clamp and the drag clamp now budget the FULL layer box (panel + the 38px options shortcut strip) instead of the panel alone — the bottom row (AI button) could previously be placed up to 38px past the viewport's bottom edge (#80; pre-existing since before v2.1.30).
- Floating button group: a saved position that is off-screen for the current viewport (e.g. saved on a wider window, or on another display) is now clamped into view at load. The restore path read `BUTTON_STYLES` before its initialization, the exception was swallowed by the restore try/catch, and the viewport clamp right after it never ran — the button group stayed invisible until any resize (#78).
- Floating button group: the visibility clamp now runs as an independent step, so a restore failure can never again skip it (the clamp is the guarantee that the group is visible).
- Hover AI button: clicking "AI" on a block no longer stays on the Google translation when the page-level mode was set to Google earlier. A page-level switch away now only suppresses in-flight AI arrivals (Q22/Q23 preserved); a stale flag no longer vetoes block-scope direct requests (#70).
