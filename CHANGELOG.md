### Fixed
- **Word path pinned a bogus CLD source language into the dictionary prompt (lone words misdetected, e.g. "Undertow" → Serbian layer)** (#151, user report). Selecting a single word and translating with AI could return a dictionary entry carrying an extra language layer the user never asked for — measured with "Undertow": `подводна струја / 暗流；潜流；底流 / a current beneath the surface of water…` plus Serbian example translations and `engleski undertow < under- + tow; … „vući, tegliti“` in the etymology — on top of the correct English/Chinese content. Root cause: the word path detected the source language with Chrome's built-in CLD (`chrome.i18n.detectLanguage`) and used only `.lang`, discarding `isReliable`. For lone words CLD is routinely unreliable **and wrong** (measured on bundled Chromium 151.0.7922.34 and Chrome-for-Testing 145.0.7632.6, identical rows: `Undertow`/`undertow`/`hello` → `sr`, `Translation` → `hr`, `apple` → `et`, `hello world` → `ky`, all `isReliable: false`; complete sentences → `en`, `isReliable: true`), and the bogus reading was pinned into the dictionary role — the wire prompt read `please act as a professional Serbian-Chinese (Simplified) dictionary, … bilingual sentence examples (at least 3) and bilingual etymology`, so the model manufactured a Serbian layer to satisfy the "bilingual" instruction (it even labels the word `[English]` — the role sentence is the command). Fix: a word-path source-language gate — the source language is named in the role only when the CLD reading is reliable AND the code is real (`isReliable === true && lang !== "und"`); otherwise the role is language-neutral (`professional bilingual dictionary translating the word into <target>; identify the word's own language yourself` — the `[<language>]` format field already asks the model to report one). `isSameLanguage` is gated on the same predicate (an unreliable reading must not drive the formatting branch), and the old `und → "English"` hardcoded fallback is gone (it folds into the neutral path). The text path's prompt carries no source language and is untouched. Test anchors: `tests/ai/fetchSSE.integration.test.js`「word-path source-language gate (#151)」W1–W5 (unreliable reading never enters the prompt / `und` no longer yields the English fallback / reliable reading still names the source — control / unreliable reading must not drive the same-language branch / `buildWordPromptRole` truth table; W1/W2/W4/W5 RED-first) + E2E `selected-panel.mjs` and `hover-panel.mjs` [E1b]: the real wire prompt captured from the mock `/request-log`, asserted premise-conditioned on the same browser's CLD reading via new `readChromeLanguageDetection` + `assertWordPromptSourceGate` helpers (`setup.mjs`) — both branches assert (no skip, no vacuous pass); the pre-fix build reproduced the user's exact symptom in both scenarios (`Serbian-French dictionary` on an `isReliable: false` `sr` reading).
- **Cross-page Google switch: an armed AI run's batch arrivals stole the display (highlight=google, page showed AI)** (#152, user report; plan 44). On GitHub Turbo: AI-translate page A → click a link to page B (auto-AI + AI highlighted) → click **Google** on B → press **Back**: the Google button stayed highlighted but the page's AI translation was re-applied by the armed restore run — a split between the announced intent and the displayed truth. Root cause: two gates read two different sources of "the run's effective intent". The E1 announcement gates on `shouldForceAiForThisRun && aiModeActive` (the D6 fix), so a run whose effective intent is google announces google — but `translatePage` restored the armed marker verbatim (`= shouldForceAiForThisRun`), keeping the AI auto-loop armed: the batch dispatched AI anyway, its arrivals passed the #70 epoch gate (no switch DURING the request) and `switchToAiDisplay` stole the display. Fix: the flag restore reads the same source as the announcement (`= shouldForceAiForThisRun && aiModeActive`) — a run whose effective intent is google disarms the AI loop; the user's one AI click re-arms it (cache-backed). Reproduced and pinned by three local experiments (user journey split; marker-deletion variants showing the arming marker belongs to the back-target page; a same-page variant showing the same wound existed in the D6-shaped cell).
